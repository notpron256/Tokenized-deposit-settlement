# Spec 001: Tokenized Deposit Settlement — Requirements and Design

Author: Sebastian Higgs
Status: Draft
Source: [intent/intent-001.md](../intent/intent-001.md)

## Summary

This spec resolves the open questions from intent-001 and specifies the fund/mint, transfer, and redeem/burn flows; the two-layer compliance model; the reconciliation approach; and the token design for a proof-of-concept tokenized deposit system on Solana devnet. The core banking ledger (mocked as Postgres) remains the sole legal source of truth for the deposit liability at all times; the Token-2022 token is a synchronized, verifiable representation of it, never a replacement for it. The gaps identified in the previous draft are now resolved: redemption burns are gated by a co-signed redemption-gateway mechanism rather than a transfer-to-omnibus convention (originally specified as the Token-2022 `PermissionedBurn` extension, then replaced — see Redeem/burn flow — after Phase 0.5 confirmed on-chain that the extension isn't supported by the locally deployed Token-2022 program), the sanctions check is specified as an on-chain PDA snapshot read (never a live call), and both the velocity limit and large-transaction thresholds are now numerically defined. What remains open — cross-system atomicity between Postgres and Solana, the redemption trigger mechanism, reconciliation cadence/alerting, and the key custody model — are called out in Areas of concern and Open questions as genuine unresolved decisions, not oversights.

## Fund/mint flow

1. A simulated event feed emits a deposit event representing an incoming client cash deposit (amount, client ID, timestamp). This is the sole trigger for minting — there is no manual entry path.
2. The event handler books the amount against the client's segregated balance in the Postgres ledger and marks it as tokenized.
3. The system mints the equivalent amount of tokens (integer cents, see Token design) to the client's associated token account (ATA).
4. Minting requires the client's ATA to already be unfrozen. A new ATA is created frozen by default (Default Account State); a client cannot receive a mint until compliance has explicitly thawed their account, which stands in for completed KYC/onboarding. This makes onboarding a hard prerequisite to the fund flow, not a parallel or later step — a deposit event for a not-yet-onboarded client should fail cleanly rather than mint into a frozen account. The same onboarding action also assigns the client's risk rating (low/medium/high) and initializes their on-chain velocity-tracking account, which the Transfer Hook reads on every subsequent transfer (see Move/transfer flow). Onboarding also captures the client's legal name, registration ID, and legal address; this real identifying data is looked up by reference at transfer time to feed the Travel Rule memo's `:50K:`/`:59:` fields, but never posted on-chain in cleartext itself (see Move/transfer flow, check 2). Like the KYC reference, none of this is verified against any real registry (Areas of concern).
5. Minting is not itself checked by the Transfer Hook (see Move/transfer flow) — Token-2022 mint instructions don't invoke the transfer hook. Default Account State is the only on-chain gate at mint time.

Sequencing gap: step 2 (ledger booking) and step 3 (on-chain mint) are two separate systems with no atomic transaction spanning both. If the ledger booking succeeds but the mint fails (or vice versa), the two systems drift — which is exactly the class of break Reconciliation is meant to catch, but no reservation/compensation logic is defined yet to prevent or auto-heal it. Flagged in Areas of concern.

## Move/transfer flow (including compliance controls)

Compliance is enforced in two layers, both at the token level rather than at the network level:

**Layer 1 — Default Account State.** Every new token account is created frozen. It cannot send or receive tokens at all until compliance explicitly thaws it. This represents onboarding/KYC-level gating: a binary, account-level switch checked before any transfer logic runs.

**Layer 2 — Transfer Hook.** A real, deployed on-chain Solana program (Rust/Anchor) is invoked on every transfer via the Token-2022 Transfer Hook extension. It runs four checks:

1. **Velocity limit** — an aggregate-dollar-value cap per client account within a fixed one-hour window: the hook tracks a running total and a window-start timestamp on the client's velocity account; each transfer adds to the running total, and if more than an hour has elapsed since window-start, the total resets to zero and a new window begins. This is a fixed-window counter, not a true sliding window — a deliberate POC scope simplification, noted here rather than left implicit. The cap is tiered by client risk rating, assigned by compliance at onboarding (the same action that thaws Default Account State — see Fund/mint flow) and read from the client's on-chain velocity account at transfer time:
   - Low risk: $5,000,000 / hour
   - Medium risk: $2,000,000 / hour
   - High risk: $500,000 / hour
2. **Travel Rule check** — rejects any transfer missing well-formed originator/recipient identifying data. This data is carried in the Required Memo extension, as four `|`-delimited fields tagged with real MT103 field numbers, in order:

   ```
   :20:<transaction reference>|:50K:<ordering customer reference ID>:<ordering customer identity hash>|:59:<beneficiary customer reference ID>:<beneficiary customer identity hash>|:70:<remittance/purpose information>
   ```

   `:50K:` and `:59:` each carry two `:`-separated values, not one — a reference ID and a cryptographic commitment, together answering two different questions:

   - **The reference ID** points at each party's own onboarding record (their Postgres primary key) — **not** their real legal name, registration ID, or legal address in cleartext. That real identifying data (captured at onboarding — see Fund/mint flow step 4) stays in Postgres exactly as before, visible only through the application's own compliance-facing views (e.g. the Onboarding page's client table), never posted immutably on a public ledger. This proves **linkage**: this transfer really does point at a specific, resolvable identity record — not just an empty pointer to nothing.
   - **The identity hash** is a SHA-256 digest of that client's name, registration ID, and legal address, canonically serialized (each field length-prefixed with its own UTF-8 byte count, so the encoding is unambiguous regardless of field content — a plain separator like `|` or `/` would let two different underlying records hash identically whenever a field happened to contain that character) and computed fresh, from the current Postgres row, at the moment of transfer. This proves **integrity**: anyone with database access can recompute this same hash from the record as it exists today and compare it against what's immutably on-chain — a match proves the record hasn't changed since the transfer; a mismatch proves it was altered afterward.

   Neither guarantee substitutes for the other. The reference ID alone can't detect a record silently edited after the fact; the hash alone (without a reference ID) can't be tied back to *which* record it was supposed to match. Together they give a defensible answer to "prove you actually captured this, not just posted an empty pointer" — linkage and integrity, checked independently. Verified independently in a completely separate toolchain from this codebase (Python + `hashlib`, reading the same Postgres row via `psql`, no shared code with the TypeScript app) — it reproduced the exact same hash the application computed, byte-for-byte.

   This is the same pattern real-world crypto Travel Rule compliance actually uses industry-wide — TRISA, Notabene, and the Travel Rule Protocol (TRP) all exchange identifying data off-chain between institutions rather than posting it on-chain — not a POC-only shortcut. **Scope boundary:** this only works because every client here belongs to one institution sharing one database; the reference resolves, and the hash is checkable, because both the sending and receiving side of every transfer can look the record up in the same Postgres instance. A genuine cross-institution transfer (this bank's client to a different institution's client) would need a real inter-institutional data-exchange mechanism — a shared Travel Rule protocol between the two institutions' own compliance systems — not just an internal database reference; that extension is explicitly out of scope here, which models intra-institution settlement only.

   Verified live against the real deployed compliance-hook program (not assumed): a reference-ID-only memo (no hash) came to 204 bytes; adding a 64-character hex SHA-256 hash to each party field brings it to 334 bytes, producing a 910-byte transaction with 322 bytes of headroom under Solana's ~1,232-byte limit. Still comfortably under the limit, though headroom is naturally smaller than the reference-ID-only design's 452 bytes — and unlike the original full-identity design (1,007 bytes, 225 bytes headroom), this memo's size is now **constant** regardless of how long a client's real name/registration ID/address actually is, since only a fixed-length hash of that data goes on-chain, never the data itself. The hook accepted it as well-formed.

   The hook parses the memo (via instruction introspection — see Technical approach) and requires all four tagged fields to be present, in order, each with non-empty content after its tag; it does not do any further SWIFT message-format validation beyond that. **This is modeled on MT103's field conventions for recognizability to a banking-ops reader — real field tags, real ordering — not a claim of live SWIFT network compliance, and it was never intended as one.** That distinction is now sharper than originally drafted: MT103 itself was retired from the live SWIFT network in November 2025, superseded by ISO 20022's `pacs.008` for cross-border payment messages. The memo format here still borrows MT103's tags because they remain the more widely recognized reference point for what "originator/beneficiary/purpose" fields look like in a payment message — but there is no implication anywhere in this design that a real MT103 message, live or historical, is being produced, parsed, or interchanged with SWIFT.

   **Two genuinely distinct on-chain rejection points can block a transfer over this requirement — not one collapsed "memo missing" check.** Token-2022's own `MemoTransfer` account extension (enabled on every client's ATA at onboarding — Phase 3, not selectively) is a recipient-side gate that Token-2022 enforces itself, *before* it ever CPIs into the Transfer Hook: it unconditionally requires *some* memo instruction to immediately precede the transfer, with no knowledge of this design's four-tag format. Only once that bare-presence gate is satisfied does control reach the hook's own structural check, which validates the memo's *content* against the four tags above. Because every onboarded client's ATA has `MemoTransfer` enabled, a transfer with no memo instruction at all is always intercepted by Token-2022's own extension first — the hook's own "no preceding instruction" branch is only reachable if `MemoTransfer` weren't enabled on the destination account, which this design doesn't allow. In practice, then, the hook-level check only ever fires for a memo that's *present but malformed* (missing a tag, wrong order, an empty tagged field), never a wholly absent one. The two layers surface genuinely distinct on-chain errors (a raw SPL Token program error for the former; the hook's own `MissingOrInvalidTravelRuleMemo` for the latter), and the backend maps both to distinct, readable rejection reasons in the Transfer flow (`backend/src/flows/transferFlow.ts`) so an operator troubleshooting a blocked transfer can tell which layer actually rejected it, rather than seeing one generic "memo missing" message.
3. **Sanctions re-screen** — checks both parties against an on-chain snapshot of OFAC's SDN list, re-checked at transfer time (not just at onboarding). The snapshot lives in an on-chain PDA, periodically synced by an off-chain process — see Technical approach for the precise mechanism. Solana-specific address coverage in the current public SDN list is likely thin-to-nonexistent, so an actual match is unlikely in practice — the point is demonstrating the mechanism (real government data, real parsing, real cross-referencing), not producing hits.
4. **Large-transaction flag** — flags any transfer of $10,000 or more, mirroring real CTR reporting thresholds. Non-blocking: the transfer proceeds, but the hook logs a complete record (transaction ID, amount, both parties, timestamp) at the point the transfer happens. Compliance handles the actual regulatory filing out-of-band, off the back of this log — the control's job is only to guarantee the record exists, not to file it.

Checks 1–3 are blocking: any failure reverts the transfer. Check 4 is non-blocking: it writes a flag (via on-chain program log / event) that an off-chain indexer picks up and records, but the transfer proceeds.

This is a deliberate architectural choice, not an implementation convenience: enforcement lives on-chain, in the token's own Transfer Hook program, rather than only in backend/off-chain logic, because on-chain, token-level enforcement is what would need to be proven before a real institution trusted this pattern in production. See Technical approach for how the sanctions check honors this without requiring the hook to make a live network call (which no on-chain program, on any chain, can do).

## Redeem/burn flow

**Resolved, verified architecture change (Phase 0.5, plan-001.md):** the mechanism below — a redemption-gateway Anchor program requiring two co-signers before it CPIs into a burn — replaces the originally assumed Token-2022 `PermissionedBurn` extension. `PermissionedBurn` is a real extension in the current `@solana/spl-token` client SDK, but the Token-2022 program actually deployed on the local validator (genesis-deployed, upgrade authority burned, so not independently upgradeable) predates it and rejects its instruction outright. This was confirmed on-chain, not assumed: an isolated test transaction using `createInitializePermissionedBurnInstruction` failed with `Invalid instruction` (custom program error `0xc`). The gateway mechanism below was then itself verified live on-chain — not just reasoned from source — before being adopted here: a one-signature redeem attempt was confirmed to fail (`Signature verification failed`, balance unchanged), and a two-signature attempt was confirmed to succeed with the on-chain balance decreasing by exactly the redeemed amount.

1. A redemption request (trigger mechanism not yet specified — see Open questions) initiates the flow for a given client and amount.
2. The client's token account (ATA) owner remains their own single key throughout — never changed to a shared/multisig authority. A naive "make the account owner a 2-of-2 multisig" approach was considered and rejected: an SPL Token account's owner field authorizes every instruction on that account (`Transfer`, `Burn`, `Approve`, `CloseAccount` alike), so a shared owner would force the bank's co-signature onto ordinary transfers too, undermining the Transfer Hook's entire purpose of unilateral, non-manual, on-chain-enforced compliance on transfers.
3. Instead, the client `Approve`s a program-derived address (PDA) — owned by a dedicated redemption-gateway Anchor program — as a scoped delegate over their ATA, for the amount being redeemed. This uses only the original, pre-Token-2022 `Approve` instruction, unrelated to the extension gap above.
4. Redemption doesn't call `Burn`/`BurnChecked` directly. It calls the gateway program's own `redeem` instruction, whose account list requires **two** Anchor `Signer`s: the client and the bank's designated compliance signer. Anchor's own account validation rejects the instruction before the handler body runs if either signature is missing — this is the token account's own program logic enforcing the co-sign gate, scoped to redemption alone, not a discipline the redemption service has to uphold on its own.
5. Before co-signing, the bank's redemption service checks the client's address against the same on-chain `SanctionsRegistry` PDA the Transfer Hook reads (see Technical approach) — the identical data source, just called directly by the redemption service rather than via the hook, since redemption doesn't route through the hook. If the client is currently sanctioned, the redemption service refuses to provide its compliance-signer signature; without it the gateway instruction fails outright, blocking the redemption.
6. Only once both signatures are present does the gateway program CPI into the base SPL Token `Burn` instruction, authorized via the PDA delegate (`invoke_signed`) — directly against the client's own token account, no intermediate transfer to a redemption/omnibus account.
7. Redemption doesn't run through the Transfer Hook's other per-transfer checks (Travel Rule, velocity) — those exist to govern value moving between two counterparties, which isn't what redemption is; a burn extinguishes the token back to cash rather than transferring it to anyone. The sanctions check is the one exception, re-applied directly per step 5: redemption is arguably the highest-value moment to catch a newly-sanctioned client, since it converts token value back into liquid fiat cash — checking only at onboarding and at ordinary transfer-time would leave this specific path open. This closes a gap identified during review, not an oversight in the original design. Beyond the sanctions re-check, the compliance signer's co-sign step is itself the compliance gate for redemption: the bank's redemption service validates the request (e.g., against the ledger) before providing its signature.
8. Once the burn is confirmed, the client's segregated cash balance in the Postgres ledger is credited for the redeemed amount, and the "tokenized" tag from the fund/mint flow is released.

Sequencing gap: burn (on-chain) and ledger credit (Postgres) are still two separate, non-atomic operations. Ordering and failure handling (e.g., what happens if burn succeeds but the ledger credit fails) isn't designed yet. Flagged in Areas of concern.

## Reconciliation

Two invariants, not one:

1. **Aggregate check** — total tokens in circulation equals the total ledger balance marked as tokenized. Fast, cheap, early-warning signal.
2. **Per-client check** — each individual client's on-chain token balance (their ATA) matches their individually segregated cash-ledger claim in Postgres, checked client by client. This is the authoritative check: an aggregate match can hide a misallocation between two clients that happens to net to zero in aggregate but is wrong per-client (e.g., client A over-credited, client B under-credited by the same amount).

A reconciliation break is any mismatch surfaced by either check. Mechanically, this spec proposes a scheduled job that (a) sums all client ATA balances and compares to the ledger's total tokenized balance, and (b) iterates client by client comparing ATA balance to ledger balance, recording any per-client mismatch as a discrete break record (client ID, expected, actual, delta, timestamp). Check cadence (real-time per-event vs. periodic batch) and the alerting/notification path for a detected break are not yet decided — see Open questions.

## Token design

- **Standard:** Solana Token-2022 (Solana devnet, not mainnet — and see Technical approach's local/devnet promotion note for how "devnet" is actually reached).
- **Decimals:** 2, matching USD cents, so all amounts are handled as integers internally (e.g., $1,500,000.25 mints as the integer `150000025`), avoiding floating-point/decimal-convention rounding errors.
- **Extensions used:**
  - **Default Account State** — new accounts default to frozen; require explicit compliance-driven thaw before they can hold or move tokens (Layer 1 compliance, see Move/transfer flow).
  - **Permanent Delegate** — grants the bank a standing delegate right over all token accounts, for compliance recovery/clawback of a compromised or sanctioned account. Distinct from the redemption-gateway mechanism below: this is for exceptional recovery scenarios, not the routine redemption path.
  - **Required Memo** — mandates a memo on every transfer, used to carry the Travel Rule originator/recipient payload as MT103-tagged fields (see Move/transfer flow for the exact structure and the MT103-retirement caveat).
  - **Transfer Hook** — points at the custom Anchor program that enforces the four transfer-time checks (Layer 2 compliance, see Move/transfer flow).
  - ~~Permissioned Burn~~ — **not used; superseded, see Redeem/burn flow.** Originally planned to designate a burn authority whose co-signature is required on every `Burn`/`BurnChecked` instruction. Real extension in the current `@solana/spl-token` SDK, but the Token-2022 program build deployed on the local validator rejects its instruction (confirmed on-chain, Phase 0.5) — not independently upgradeable there, since its upgrade authority is burned at genesis. Replaced by a redemption-gateway Anchor program (client `Approve`s its PDA as a scoped delegate; the gateway's own instruction requires the client and the bank's compliance signer as co-signers before it CPIs into the base `Burn` instruction) — verified live on-chain, not assumed. This keeps redemption compliance-gated at the token/program level without touching the ATA's owner field, so ordinary Transfer authorization is unaffected (see Redeem/burn flow).
- **Per-client velocity account** — a compliance-writable on-chain account per client, storing their risk rating (low/medium/high), a running velocity total, and a window-start timestamp. Initialized at onboarding alongside the Default Account State thaw; read (and updated) by the Transfer Hook on every transfer (see Move/transfer flow, check 1).
- **Sanctions registry PDA** — a single on-chain account holding a periodically-synced snapshot of Solana-format addresses drawn from OFAC's SDN list; read by the Transfer Hook on every transfer (see Technical approach for the sync mechanism). Each entry is `{ address: Pubkey, source: u8 }`, where `source` (`0` = real OFAC SDN data, `1` = a synthetic test entry — see Areas of concern in the previous draft, now resolved in Phase 1d, plan-001.md) is a fact of the on-chain data structure itself, not a label applied later off-chain. **Forward requirement, not yet built:** whichever phase builds the Compliance/Transfer/Redeem UI must surface this field visibly wherever a sanctions hit or registry entry is shown to a person — a "SYNTHETIC (TEST)" vs. "REAL (OFAC SDN)" badge, driven by the on-chain `source` value, not a hand-maintained UI list — so nobody looking at a blocked transfer could mistake a synthetic test hit for a real OFAC match. Same STUB/LIVE-style honesty labeling discipline as the previous project. (plan-001.md's Phases 5–8 already commit to this in their done-tests; recorded here too since this is the standing design doc, not just the execution checklist.)
- **Authority model:** mint authority, freeze authority, permanent delegate authority, the redemption-gateway compliance signer, and the sanctions-registry sync authority are all bank-controlled. The specific custody arrangement (single key vs. multisig, which service holds which authority) is not yet defined — see Open questions.

## Technical approach

- **Chain:** Solana devnet — reached deliberately, not directly. This project builds and tests against a private local `solana-test-validator` first (fast, free, instantly resettable), then promotes each piece to public devnet only once it's stable and tested, so it becomes independently observable by anyone — not just this machine — via the standard Solana Explorer (no custom RPC configuration) and third-party explorers like Solscan. As of the last promotion: compliance-hook, the mint (with its three extensions), and the sanctions registry are live on devnet, at the same program ID as local (the deploy keypair is reused across networks; only the on-chain state differs per network). The redemption-gateway program is **not** promoted — it's still only the Phase 0.5 spike, not the real Phase 8 build, so it remains local-only until Phase 8 is actually built, then gets promoted the same way. `SOLANA_RPC_URL`, `DATABASE_URL`, and `backend/keys/<network>/` always move together as one group (see README.md's Networks section and .env.example) — Postgres client data is never shared between the two networks, kept in separate databases entirely.
- **Local-validator rent costs do not transfer 1:1 to devnet — a genuine, verified protocol-parameter difference, not a measurement artifact.** `solana-test-validator`'s default genesis sets the `Rent` sysvar's `lamports_per_byte_year` to `6960`, versus real Solana devnet's live value of `5080` — a ~27% difference in rent-exemption cost for identical account sizes. `exemption_threshold` (`1.0`) and `burn_percent` (`50`) are identical on both, so this one parameter is the entire cause. Verified by reading each cluster's `Rent` sysvar account directly and decoding it by hand — not just inferred from observed deploy costs, though an actual same-binary deploy to both clusters (compliance-hook, 231,544 bytes) independently reproduced the identical ratio (1.61275032 SOL locally vs. 1.17712236 SOL on devnet, a 0.7299 ratio matching `5080/6960` almost exactly). **Practical implication:** local-validator rent-cost estimates will always overestimate real devnet/mainnet costs by roughly this ratio — any future cost planning based on local-validator testing should apply this ~73% correction factor rather than assume costs transfer 1:1 between environments.
- **Token program:** Token-2022, with the extensions above.
- **Transfer Hook program:** Rust/Anchor, deployed to devnet (promoted from local — see the Chain entry above), implementing the four checks in Move/transfer flow.
- **Core ledger:** mocked as a Postgres table (or small set of tables) representing segregated per-client cash balances — the system's sole legal source of truth.
- **Settlement-finality gating — "settled" vs. Solana's "finalized":** every ledger row that claims a completed on-chain action (`deposit_events`, `transfer_events`, `redemption_requests` status; `clients.status = 'active'`) moves through `pending_chain -> confirmed -> settled` (or `failed`), not straight to a terminal state once the transaction lands. These two words are kept deliberately distinct and must not be conflated:
  - **"Finalized"** is Solana's own technical commitment level — the strongest one the cluster offers, meaning the block containing the transaction has been voted on by enough of the cluster that it's no longer possible (short of a hard fork) for it to be dropped. `"confirmed"`, one level below, means a supermajority has voted for the block, but in principle it could still be abandoned in a fork before finalizing.
  - **"Settled"** is the business/banking term this system's ledger actually stores and shows: value has irrevocably moved. It's the human-facing status, gated on Solana's `"finalized"` commitment as its technical trigger condition — a row only becomes `settled` once its transaction has separately reached `"finalized"`, never merely `"confirmed"`.

  Concretely: every flow first sends and waits at Solana's `"confirmed"` commitment (an explicit `{ commitment: "confirmed" }`, not an inherited default — see Areas of concern for why that distinction mattered) and writes the ledger row's `confirmed` status plus the transaction signature at that point. Only then does it separately wait for `"finalized"` commitment on the same transaction (`backend/src/solana/finality.ts`); once that resolves, the row moves to `settled` and — for flows that move value (`deposit_events`, `transfer_events`) — `ledger_balances` is updated in the same step, never before. If the wait for `"finalized"` fails, the row stays at `confirmed` rather than moving to `failed` (the on-chain action genuinely happened) or silently `settled` (it isn't provably irreversible yet); a row stuck at `confirmed` is exactly the kind of anomaly Phase 9 reconciliation is meant to surface. The same gating applies to onboarding: a client is inserted with `status = 'confirmed'` immediately after the onboarding transaction confirms, and only flips to `'active'` — the status every other flow checks before allowing a client to transact — once finalized.
- **Deposit trigger:** a simulated event feed (not manual entry) emits synthetic deposit notifications that drive the fund/mint flow.
- **Sanctions registry sync:** no on-chain program, on Solana or any other chain, can make a live network call during its execution — this is a universal constraint, not a Solana-specific gap. The fix is the same pattern the previous project validated with the Chainalysis oracle: an off-chain sync process, running on a fixed daily cadence, fetches the public OFAC SDN list, filters it down to entries formatted as Solana-shaped addresses (base58-encoded 32-byte pubkeys, pulled from the SDN list's digital-currency-address fields), and writes that filtered set into a single on-chain `SanctionsRegistry` PDA. Only the sync authority's signature (a bank-controlled off-chain service keypair, distinct from the mint/freeze/permanent-delegate authorities and the redemption-gateway compliance signer) can update the PDA's contents. The Transfer Hook only ever reads it — a fast, ordinary on-chain account read at transfer time, never a live call to OFAC or any external service. Because Solana-format addresses are a small, likely near-empty subset of the full SDN list, the filtered on-chain set stays small enough to read cheaply within the hook's compute budget.
- **Off-chain indexer:** a service that listens for on-chain program logs/events from the Transfer Hook and durably records *all* transfer activity it independently observes — not only large-transaction flags and blocked-transfer reasons, but every transfer, reconstructed purely from on-chain data (see plan-001.md Phase 6's broadened scope). This exists for compliance/ops visibility (the hook itself cannot write anywhere but the chain) and, just as importantly, to give Phase 9 reconciliation and the Compliance page a record that's genuinely independent of the backend's own Postgres writes, rather than one that would just mirror them.
- **Reconciliation job:** a scheduled off-chain process implementing the two invariants above, reading both the Postgres ledger and on-chain token account balances.

## Areas of concern

These are gaps that could block implementation without a follow-up decision:

- **No cross-system atomicity between Postgres and Solana.** Both fund/mint and redeem/burn involve a ledger write and an on-chain instruction as two separate, non-atomic steps. Neither ordering nor compensation/retry logic for a partial failure (one side succeeds, the other doesn't) is defined. This is precisely the failure mode reconciliation is designed to detect, but detection isn't prevention — a partial failure would sit as an open break until the next reconciliation run.
- **Fund, Transfer, and onboarding originally settled the ledger at Solana's "confirmed" commitment, not "finalized" — a real gap, found and fixed, not a deliberate scope decision.** `getConnection()` constructs its `Connection` with default commitment `"confirmed"` (`backend/src/solana/authorities.ts`); every `sendAndConfirmTransaction` call in Fund/Transfer/onboarding omitted an explicit commitment override and so silently inherited it, and the post-transaction balance read-backs (`getAccount(..., "confirmed", ...)`) did too. That meant a ledger row could be marked as its terminal successful status — `deposit_events`/`transfer_events` at `confirmed` (there was no `settled` value yet), `clients.status = 'active'` — the moment a transaction reached `"confirmed"`, one commitment level short of the point Solana itself guarantees the transaction can't still be dropped. Fixed by making every commitment level explicit rather than inherited, and inserting a genuine wait for `"finalized"` (`backend/src/solana/finality.ts`) between the existing `confirmed` intermediate state and a new terminal `settled` state — see Technical approach's "settlement-finality gating" entry for the full mechanism. Caught via an explicit audit request, not discovered by a failure in practice; on a single-node local validator the confirmed-to-finalized window is small enough that this was never likely to bite during this POC's own testing, but the axiom it violates — the ledger must never claim more certainty than the chain has actually reached — holds regardless of how unlikely a given environment makes the failure mode.
- **Authority/key custody undefined.** Mint authority, freeze authority, permanent delegate authority, the redemption-gateway compliance signer, and the sanctions-registry sync authority are all bank-controlled per Token design, but the actual custody model (single key, multisig, which service/process holds each one, how thaw/burn/clawback/registry-update actions get authorized) isn't specified.
- **Client key custody is bank-side for this POC — a deliberate scope decision, not an oversight.** Simulated clients have no independent external wallet; the backend custodies each client's token-account signing key alongside the bank's own authority keys, so every flow can be driven end-to-end by clicking through the demo UI without a separate per-client wallet/signing experience. This is a real simplification relative to how a production deposit-token system would work — e.g. JPM Coin's actual model has the client control their own key via a client-side framework, not the issuing bank custodying it invisibly. Reintroducing client-side custody (a signing UX distinct from the bank's own authority keys) is deferred, not designed here.
- **Onboarding trusts a supplied KYC reference — a deliberate scope decision, not an oversight.** Onboarding (Phase 3, plan-001.md) requires the operator to enter a free-text "KYC reference" (a case/ticket ID) before a client can be onboarded, recording where real KYC and risk-rating approval is claimed to have happened out-of-band. This reference is stored on the client record as an audit-trail entry and a forcing function — the UI will not let onboarding proceed without one — but it is **not verified against any real KYC/compliance system**: nothing checks that the reference is genuine, that it corresponds to a real case, or that approval actually happened. Same honesty pattern as the STUB/LIVE labeling used elsewhere in this project (and its predecessor) for data that looks real but isn't independently verified. A real deployment would integrate with an actual KYC/case-management system and verify the reference (or replace it with a live lookup) before onboarding could proceed; that integration is out of scope here.
- **Registration ID and legal address are supplied, not verified — same honesty pattern as the KYC reference above.** Onboarding also requires an entity/registration ID and legal address. Neither value is checked against any real corporate registry or address-verification service — the point is demonstrating that Travel Rule identity resolution works end-to-end (a memo reference ID resolves to a real, structured identity record via the application's own compliance views), not proving any of that record's contents are true. Clients onboarded before these fields existed carry self-documenting placeholder text rather than blanks or fabricated values (see Move/transfer flow, check 2) — a decision made explicitly rather than silently, given re-onboarding them would have meant abandoning their real on-chain balances and regenerating new keypairs/ATAs, a materially more disruptive operation than adding two backfilled columns.
- **Travel Rule memo carries a reference ID, not cleartext identity data — a deliberate privacy design, not a POC-only shortcut, but with a real scope boundary.** `:50K:`/`:59:` hold each party's client ID rather than their name/registration ID/address directly (Move/transfer flow, check 2) — the same off-chain-exchange pattern real-world crypto Travel Rule compliance uses industry-wide (TRISA, Notabene, the Travel Rule Protocol). It only works here because every client belongs to one institution sharing one Postgres database, so the reference is always resolvable by whoever needs to resolve it. A genuine cross-institution transfer (this bank's client to a different institution's client) would need a real inter-institutional data-exchange mechanism between the two institutions' own compliance systems, not just an internal database reference — that extension is out of scope; this POC models intra-institution settlement only.
- **The devnet sanctions registry currently contains only the `SyntheticTest` entry — promoting it to devnet didn't and couldn't add real OFAC data, because Phase 7 (the real OFAC SDN sync job) hasn't been built yet.** No code in this repository fetches, parses, or filters the real public OFAC SDN list — only `backend/scripts/seed-sanctions-registry.ts` exists, which writes a single synthetic test entry pointing at a normally-onboarded client (e.g. Sanctioned Test Corp). This is true on both local and devnet; moving the registry to a public network is a promotion of infrastructure and mechanism (the PDA, the on-chain read, the sync-authority-gated write), not a promotion of data that doesn't exist yet. Once Phase 7 is built, its real-sync writes need to preserve the synthetic entry across a full-replace sync (see the Sanctions registry PDA entry above and `update_sanctions_registry`'s own doc comment) on whichever network it's pointed at.

## Open questions

- **Cross-system atomicity** — see Areas of concern; no ordering or compensation logic yet for a partial failure between the Postgres ledger and Solana on either the mint or burn path.
- **Redemption trigger** — is the redemption request simulated the same way the deposit event is (per the intent doc's resolved decision), or does it originate differently (e.g., an explicit API call standing in for a client instruction)?
- **Reconciliation cadence** — real-time per-event, or periodic batch (and if batch, what interval)?
- **Reconciliation break routing** — who or what receives a break alert (ops, compliance, both), and in what form (dashboard, log, paging)?
- **Authority/key custody model** — see Areas of concern; needs a decision before deployment scripting, though it may be reasonable to defer with a placeholder single-key setup for the POC specifically.
